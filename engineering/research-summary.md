## Ch02 - The Runtime

**How it executes.** PHP runs on the Zend Engine, request-per-process/thread, shared-nothing by default: no in-process state survives between requests unless the serving layer is explicitly built to keep the app booted. Source: php.net manual (rolling, no fixed date; cite as "the PHP manual, current," checked 2026-09-17).

**Opcache.** Bundled with PHP since 5.5, but it is a `zend_extension` that must be loaded in `php.ini` - it is not automatically active just because PHP is installed; most distro packagers turn it on by default, PHP core itself does not. Source: php.net/manual/en/opcache.installation.php, checked 2026-09-17. Worth stating precisely rather than saying "on by default."

**JIT (PHP 8.0).** The JIT RFC itself is explicit that the compiler helps CPU-bound/numeric code far more than typical web-request code, and it ships its own WordPress benchmark showing almost no gain: **326 req/sec with JIT vs 315 req/sec without**, because a typical request's bottleneck is I/O (database, network) and FPM/HTTP overhead, not CPU. Source: wiki.php.net/rfc/jit, checked 2026-09-17. This is the single best sourced fact for WRITING.md's rule against presenting synthetic JIT gains as web-application gains - it comes from the RFC itself.

**Serving models.**
- FrankenPHP's own docs describe "worker mode" as keeping the app booted in memory across requests; superglobals (`$_GET`, `$_POST`, `$_COOKIE`, `$_FILES`, `$_SERVER`, `$_REQUEST`) are reset between requests automatically, but `$_ENV` is not, and the docs themselves warn "PHP was not originally designed for long-running processes," recommending periodic worker restarts to bound memory leaks. Source: frankenphp.dev/docs/worker/, checked 2026-09-17.
- RoadRunner: a Go-based application server managing a pool of long-lived PHP worker processes; each worker still handles one request at a time and persists across requests rather than being torn down. **NEEDS DIRECT FETCH** of docs.roadrunner.dev (roadrunner.dev/docs/... redirects there) - current characterization traces to a comparison blog, not the project's own docs.

**Async ecosystem** (each claim from the project's own README):
- Swoole: "an event-driven asynchronous & coroutine-based concurrency networking communication engine... written in C++ for PHP"; hooks PHP's blocking I/O calls and converts them to non-blocking under the coroutine scheduler. Source: github.com/swoole/swoole-src README, checked 2026-09-17.
- ReactPHP: "a low-level library for event-driven programming in PHP," built around an event loop, described by the project itself as suited to servers/clients handling large numbers of concurrent connections. Source: github.com/reactphp/reactphp README, checked 2026-09-17.
- AMPHP: not independently re-verified this pass. **NEEDS DIRECT FETCH** of github.com/amphp/amp README.
- Fibers (PHP 8.1): cooperative, single-stack-at-a-time coroutines scheduled by userland via `Fiber::suspend()`/`Fiber::resume()` - concurrency, not parallelism, no OS threads. Source: php.net/manual/en/language.fibers.php, checked 2026-09-17.

**The limit for this chapter:** no native multithreading in userland. `parallel` and `pthreads` exist as PECL extensions for true OS-thread parallelism but are third-party, narrowly adopted - worth naming as "exists, but niche," not omitting.

## Ch04 - Performance

- **TechEmpower Framework Benchmarks were discontinued on 24 March 2026** (GitHub repo now archived). The last completed round is **Round 23, published 17 March 2025**, covering 330+ framework implementations. This discontinuation is itself worth stating in the book, dated, since WRITING.md requires round/hardware/test/date for every benchmark and a reader will otherwise go looking for a "Round 24" that doesn't exist. - Round 23's Fortunes test (a realistic mixed workload, not raw JSON serialization) had a PHP-based framework at roughly 16,800 requests/second in results surfaced via search. **NEEDS DIRECT FETCH** of techempower.com/benchmarks/#hw=ph&test=composite&section=data-r23 to confirm the exact figure, the exact framework/setup tested, and where it sits relative to Node.js, Python, Java, C#, Go, and Ruby entries specifically - only Laravel's position was confirmed via snippet.

- **Gap**: no clean, single, primary-source multiplier for PHP versus Go/Rust/Java on sustained CPU throughput - the benchmarksgame's own pairwise pages for Rust and Go 404'd on direct URL guesses. Recommend pulling the site's machine-readable summary table before writing this chapter, or leaning on TechEmpower Round 23 for web-request throughput and being explicit that it measures something different from raw CPU benchmarks.
- A single-author benchmarking blog (phpbenchlab.com) was found claiming Go/Node.js beat PHP+JIT on a CPU-bound web task, and separately that JIT gives a same-language +110% throughput improvement over JIT-disabled PHP - **not usable as a primary/appendix-grade source** per WRITING.md's bar, but the same-language JIT-on/off comparison is a legitimate, clearly-labelled illustrative data point if the book wants one.

## Ch07 - Cost

- **PHP License**: free, OSI-approved. Version 4 (Modified BSD/BSD-3-Clause) applies from PHP 8.6 onward per php.net; PHP 8.4/8.5 (today's floor per the polyglot book's fact sheet) ship under License 3.01, also OSI-approved and permissive. Source: php.net/license/index.php, checked 2026-09-17. **Decided 2026-09-18: treat PHP 8.4 as the book's floor** (current active-support standard per Ch08), with 8.5 named explicitly as the newest release. That means License 3.01 is the version this book documents as live; License 4's 8.6 trigger is mentioned as upcoming, not treated as already in effect. Still needs the direct fetch of php.net/license/index.php to confirm nothing has moved.
- **Packagist/Composer ecosystem**: 468,201 packages, 5,822,307 versions, roughly 199.8 billion cumulative installs since 13 April 2012. Source: packagist.org/statistics, checked 2026-09-17. This is a live counter - the chapter should describe magnitude ("nearly half a million packages," "close to 200 billion installs"), not the exact digit, per WRITING.md's rounding rule.
- **Hosting cost**: no clean neutral primary source for a "PHP is cheap to host" figure - any specific cost claim traces back to a hosting vendor, which WRITING.md forbids as a source. Recommend making the argument from the architecture fact instead (stateless, low per-request memory, no persistent runtime required), not from a cost statistic.
- **Salary/job-demand**: same gap as Ch06 - not resolved this pass.
- **Sovereign hosting and infrastructure portability (new angle, 2026-09-18)**: the evaluator question is "does choosing PHP lock me into one cloud vendor, and can I deploy where local law or procurement requires (data localization, sovereign-cloud mandates, on-premise, bare metal)". **Architectural fact, directly sourced, no vendor needed**: PHP-FPM's process model requires only a POSIX-compliant OS, a web server and a runtime - no proprietary orchestration layer - to serve requests at scale. Source: php.net/manual/en/install.fpm.php, already cited in Ch02/Ch05, reusable here without a new fetch. This is a legitimate, appendix-grade fact because it's a description of what the software requires, not a claim about any specific deployment target.
- **Where the reviewer's draft text needs editing before it can go in a chapter**: the suggested passage names OVH, Hetzner and "local telecom clouds" as example sovereign-hosting destinations, and AWS Lambda/Azure Functions as the vendor-locked contrast. WRITING.md section 3 bans hosting, cloud and SaaS names outright except when the book is citing that company's own published benchmark or survey - naming them as *example deployment targets* is exactly the case the rule exists to prevent, not the carve-out. **Fix**: keep the architectural claim (no proprietary orchestration required) and the contrast (a runtime built around vendor-specific serverless primitives is harder to relocate) entirely generic - "a bare-metal or sovereign-cloud provider", "a proprietary serverless orchestration layer" - with no company named on either side of the comparison.
- **The honest limit this argument needs (WRITING.md section 4)**: the portability claim is true of the PHP runtime itself, not of a team's whole operational stack. A team that has also adopted cloud-specific managed databases, queues or the observability/APM tooling flagged in the 2026-09-18 review (see the new cross-cutting gap items below) has already re-introduced vendor lock-in at those layers regardless of language. State the sovereignty argument as "the runtime does not force cloud lock-in", not as "a PHP application is portable", so the chapter doesn't overclaim.
- **Data-localization / sovereignty law context**: if the chapter wants to name a concrete regulatory driver (GDPR, or a specific country's data-localization law) as the reason a leader would care, the primary source is the regulation's own published text (for the EU, eur-lex.europa.eu), not a law firm's or vendor's summary of it. **NEEDS DIRECT FETCH** if this level of specificity is wanted; otherwise the chapter can describe the driver generically ("data-residency requirements in some jurisdictions") without citing a specific law, which avoids the fetch entirely and ages better.

## Ch09 - Where PHP Is the Wrong Choice

This chapter has the most editorially interesting research: two findings complicate the "obvious" limits, which is exactly the kind of honesty WRITING.md wants, but both need careful framing so the chapter doesn't overclaim in either direction.

- **No native multithreading**: solid, current, true today. Fibers (8.1) give concurrency via cooperative scheduling, not parallelism; no OS threads. `parallel`/`pthreads` exist but are niche third-party extensions. Source: php.net/manual/en/language.fibers.php.
- **CPU-bound compute - the surprise**: PHP is *not* behind Python on the Computer Language Benchmarks Game; it's ahead, by roughly 1.5-2x on the tasks tested. The defensible limit is PHP versus compiled/JIT-mature languages (Go, Rust, Java, C#), not versus Python or Ruby - **the chapter must not repeat the "PHP is slow" cliché against the wrong comparison set**. A clean single-source multiplier against Go/Rust specifically is still an open gap (see Ch04).
- **Mobile/desktop native apps - weaker limit than assumed**: NativePHP packages Laravel apps into desktop (Electron-based) and mobile apps, with its own docs claiming production app-store deployments as of 2026 (nativephp.com/docs/...). This is real but young, single-framework-dependent (Laravel), and sits outside WRITING.md's fixed alphabetical framework list. **Decided 2026-09-18: name NativePHP once, dated, as a community-driven exception** - treated the way an organisation would be named (one mention, with its date), not folded into the alphabetical framework list and not repeated elsewhere in the chapter. Leaving it out entirely reads as dated in 2026 (the r/PHP thread independently surfaced it, unprompted, as the community's default answer here); naming it more than once would over-index a single, young, framework-specific project against WRITING.md's neutrality rules. The honest framing stays "no first-party toolkit; a community solution exists, is new, and is unproven at the scale of Swift/Kotlin/MAUI," not "impossible."
- **Machine learning/data science**: real gap, but no clean neutral survey figure found for "language share among ML practitioners" specifically (Kaggle's 2025 survey dataset wasn't fetchable this pass). Recommend the ecosystem-density argument instead: no PHP equivalent to NumPy/pandas/PyTorch/TensorFlow, checkable via Packagist category search or php.net's extension index, rather than a borrowed usage percentage that isn't actually about ML.
- **Long-running processes**: real, "partially solved" needs precision. FrankenPHP's own docs are unusually candid: "PHP was not originally designed for long-running processes," worker mode mitigates but does not eliminate this (periodic worker restarts are the documented workaround for memory leaks). Fair, honest, non-FUD, and sourced straight from the vendor's own admission.
- **No generics**: solid. PHPStan and Psalm both read the same `@template` docblock convention, enforced only at development time via static analysis, never by the engine. Current sourcing is secondary (comparison blogs) - **needs direct fetch** of phpstan.org/writing-php-code/generics and psalm.dev/docs/annotating_code/templated_annotations/ before citing in the appendix.
- **Hosting ecosystem on old versions**: same W3Techs figures as Ch08 - nearly 8% of the PHP install base is on PHP 5 (EOL since 2018/2019), 28% on PHP 7 (last branch EOL November 2022). Solid, dated, and it's a market-reality caveat, not a claim about the current language - exactly the distinction WRITING.md wants drawn.

## Practitioner sentiment check - r/PHP thread, not citable, orientation only

Per WRITING.md section 3 ("No individuals as authorities") and the citation bar in section 4, nothing below is usable in a chapter or the sources appendix - it's an anonymous, unmoderated forum thread, the opposite of a primary source. Treat every bullet as a lead, not a fact.

- **Confirms the existing Ch09 list, unprompted.** No native multithreading, no async/await, no generics were each named independently by multiple commenters without being primed by each other. That's a reasonable signal the chapter's fixed limits list matches what practitioners actually reach for first, not just what the RFC trackers show.
- **A sharper, separate limit from generics: no native typed arrays/collections.** One detailed reply (from a commenter who reads as a static-analysis-tooling contributor) explains PHP core treats typed arrays and generics as coupled problems, that the third-party `ds` (data structures) PECL extension is the closest fix and is "slightly bit-rotted" and broken on 8.6. **NEEDS DIRECT FETCH** of pecl.php.net/package/ds and its php-src RFC history before this becomes a Ch09/appendix line; right now it's a single forum claim.
