# Writing Automated Tests

Every piece of code in this book so far has been verified the same way: you ran it and looked at the output. That works fine for a guessing game. It stops working the moment your project has more than a handful of functions, because you can no longer hold "everything that might have broken" in your head every time you change a line. Automated tests are how you outsource that job to the computer, which never gets tired of running the same check for the thousandth time and never forgets to run it at all.

PHP's testing ecosystem has one clear default: [PHPUnit](https://phpunit.de/). It's been the de facto standard for close to two decades, it's what nearly every library and framework in the PHP world uses internally, and it's the tool this chapter will teach. You already know how to pull it into a project: it's a Composer package, installed the same way you met in [Chapter 1](ch01-03-hello-composer.md).

This chapter covers three things in order: how to actually write a test and the assertions PHPUnit gives you to make claims about your code's behavior; how to control which tests run and when, once you have more than a handful of them; and how to organize a growing test suite so it stays navigable instead of becoming its own maintenance burden. By the end, testing won't be an afterthought bolted onto finished code; it'll be part of how you write the code in the first place, which is exactly the habit [Chapter 13](ch13-00-a-cli-project.md) leans on when it builds a small project test-first.
